Workspace webhook delivery, retry, and version recovery

Document version: 1.0.0. Source: Northstar Workspace internal support runbook. License: course_synthetic. PII classification: none.

Support visibility: internal. This runbook covers HTTP 404 delivery failures, retry behavior, duplicate delivery, and version-safe troubleshooting.

Required facts before diagnosis

Preserve the exact HTTP status, webhook version, subscribed event name, endpoint host and path, event identifier, request identifier, delivery attempt count, and delivery timestamp. Do not infer an endpoint path from a status code alone.

HTTP 404 sequence

  1. Confirm the delivery log records HTTP 404 and identify the exact webhook version and endpoint path used for that attempt.
  2. Ask the customer to verify that the public HTTPS endpoint and route for that version are deployed and reachable.
  3. Confirm the subscription event name and organization scope match the intended consumer.
  4. When the customer confirms a corrected route, replay one failed delivery with the original event identifier.
  5. Confirm a 2xx response within ten seconds and exactly one resulting business event.

Retry and idempotency

Retries and a manual single-delivery replay can produce more than one delivery attempt for the same event identifier. Consumers must deduplicate by event identifier. Support must not recommend a bulk replay, disable deduplication, or treat a repeated attempt as a new business event. The HTTP status and webhook version remain part of the incident record across retries.

Escalation and safety boundary

Bulk replay and endpoint ownership changes require a support lead. A service credit may only be proposed when verified customer impact is documented with evidence; it always follows the existing human approval path. If the delivery log is unavailable, the card must request clarification or abstain rather than construct a diagnosis.
